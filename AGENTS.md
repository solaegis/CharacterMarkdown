## Learned User Preferences

- When asked to implement an attached `*_plan.md` build plan, do not edit the plan file; update the character profile export, alignment checklists, and related artifacts only. Do not recreate todos when the user says todos already exist; mark them in progress and complete them in order. When asked for **next steps** toward a plan, gap-analyze the live profile export against the plan checklist and prioritize remaining Phase items — do not rewrite the plan unless asked. Pre-weapon-swap / front-bar-only characters get a single compressed front-bar bridge from currently unlocked skills (not a dual-bar target paste); verify skill-line unlock ranks before recommending purchases; treat temporary off-plan weapons used only to unlock swap as non-investment placeholders and keep advising toward the plan’s weapon identity.
- User expects ESO mechanical correctness in example build documentation: use **current in-game names** (Champion Point stars, skill morphs)—not deprecated labels (pre–Update 29 CP; pre–U49 Dragonknight paths such as **Fiery Breath → Noxious Breath** or **Spiked Armor → Hardened Armor** are invalid); skill bars must match equipped weapon type, each morph appears at most once, and bar tables include ultimates; default layout puts **offense on the front bar** (e.g. Destruction) and **healing/support on the back bar** (Restoration) unless the user specifies otherwise; when a build uses **both melee and ranged** weapons, **melee is front** and **ranged is back** (e.g. Dual Wield / Two-Handed front, Bow back)—do not put Bow on front with melee on back; document **slotted morph names as shown in the skills UI** (not unmorphed base or wiki-only labels—e.g. **Inspired Scholarship → Recuperative Treatise**, not **Tome-Bearer's Inspiration** after morphing); Champion Point constellations are capped at **4 stars per constellation**; Daedric summons use **slot 5 on both bars** (same ability) or are omitted entirely—never on one bar only. Use real ESO ability lines only (**base → sibling morphs**)—never treat a morph as the base (e.g. **Scorch → Deep Fissure / Subterranean Assault**, not Subterranean Assault as base); correctly classify **Ultimates vs morphs vs passives vs companion special activates** (e.g. **Feral Guardian** is the Animal Companions Ultimate → **Eternal Guardian / Wild Guardian**; **Guardian's Wrath** is the bear special activate, not a morph or separate bar skill; **Continuous Attack** is an Assault **passive**, not a **Rapid Maneuver** morph—those morphs are **Charging Maneuver** / **Retreating Maneuver**); do not invent skill names or tell the user to morph from an already-morphed skill to a nonexistent ability. When a plan's Trinity **drops a skill line** (e.g. **Shadow** replaces **Earthen Heart**), target/post-50 bars and rotations must not keep skills from the dropped line (e.g. **Earthshield Mantle**). Until goal skills are unlocked, recommend bridging front/back bars using **only skills the character currently has**, and never recommend a skill that is still locked by skill-line rank (e.g. do not suggest buying **Grim Focus** before Assassination rank 42). Always consider subclassing when creating or heavily revising build plans (`template_plan.md` / Trinity).
- When the user frames a build as class-identity-first (e.g. true necromancer first), keep native class skill lines by default; only subclass a line when the foreign line clearly outperforms the native one it replaces. For theme/aesthetic-first builds (e.g. pugilist/monk), prioritize the visual fantasy and power within that frame; when the user rejects obvious race/class pairings, offer stronger alternatives; subclass skills may be used without reframing the character into that fantasy (e.g. assassin skills without making the character an assassin). When designing greenfield characters for uniqueness on a megaserver, prefer class niches and races underused on that server's solaegis roster (not only power-optimal defaults). When reviewing one character's plan for improvement, do not use other characters' builds as the baseline unless asked.
- ESO **companion gear is separate from player character gear** — only **Companion's** weapons/armor with companion-only traits (Quickened, Aggressive, Bolstered, etc.); never fictional **"Companion's {player set}"** names, player sets (Julianos, Clever Alchemist, Divines), or **5-piece set bonuses**; acquire via merchant whites and **Superior+** drops while the companion is active — **not** via player crafting handoff from **Gear and crafting**. Match Companion's **weapon type** to the plan combat style and slotted abilities (e.g. Bow with Piercing Arrow / Sniper's Mark when the plan is Bow DPS — do not leave dual wield on a bow bar).
- Target gear in build plans must always be **craftable** (account crafter / crafting stations). Do not plan primary loadouts around overland farming, dungeon monster sets, trial drops, or other non-crafted acquisition unless the user explicitly asks for an exception.
- When changing addon settings (defaults in `src/settings/Defaults.lua`, LAM panel labels/checkboxes/presets in `src/settings/Panel.lua`, or `ToggleAllSections`), always update `docs/settings-presets-matrix.md` in the same change so factory defaults and every preset column stay accurate. When preset definitions gain new toggles, users must **re-apply the preset**—saved settings do not auto-enable new checkboxes. When a LAM preset enables sections that lack generators or `Markdown.lua` registry wiring, implement or wire the missing output rather than disabling preset checkboxes or narrowing preset scope.
- Do not bulk-reformat existing `examples/solaegis/{na,eu}/*_plan.md` files to the canonical structure unless the user explicitly asks; apply the exemplar outline to new and heavily revised plans only.
- For LAM **Build Notes** paste text from a plan, prefer **roleplay voice** over mechanical build details; markdown is fine within the ≤1,900-character limit (Custom Title stays ≤100 chars). Avoid **Sheogorath** / Mad God / Misrule-carnival framing in character build roleplay unless the user explicitly asks for it.
- When creating or heavily revising a solaegis `*_plan.md`, consult and update [`docs/collectibles_companion_ledger.md`](docs/collectibles_companion_ledger.md): use **account tiers → per-character shortlist → primary table** for mount/pet/costume (owned-first, appropriateness-first; diversify when roughly equal within the same megaserver; no numeric cap on primary diversity across alts); shortlists cap at ≤3 S / ≤5 A names per kind; refresh tiers via personal skill `eso-collectibles-tier-ledger` (one megaserver per run; do not invent ownership from incomplete exports) when ownership exports change; **companions: account has access to all companions** — pick best-fit by stage only (Primary now / Secondary / Goal); never filter or defer a companion for unlock/ownership; no diversity soft-cap; companions are not re-tiered by the collectibles skill; do not mass-rebalance other plans solely for diversity.
- For large addon review/fix passes, prioritize by severity (correctness and crash bugs first), validate with luacheck/StyLua/tests, and work in reviewable batches.
- When asked to confirm an example export's **default settings** output, audit H2 sections against **factory defaults** and likely LAM presets (do not assume Reset to Defaults); use `scripts/validate_example_preset.py` (`--profile factory-defaults`, `solo-pve`, or `auto`) and `docs/settings-presets-matrix.md`. Solo PvE exports should include **World Progress** and **Appearance** H2 sections; **Build Notes** is optional when empty.
- When drafting ESOUI posts, comments, replies, or the addon description (`README_ESOUI.txt`), write in **BBCode** (`[B]`, `[I]`, `[LIST]`, `[*]`, `[URL]`, `[CODE]`, `[color=hex]` without `#`, …), not Markdown — ESOUI renders BBCode only.

## Learned Workspace Facts

- Character examples live under `examples/{account}/{location}/{slug}.md` (identity = account + location + slug; same slug allowed across different accounts or locations, not duplicated for the same account and location). Slugs are **lowercase with underscores** (not hyphens), matching the character name—not placeholder filenames like `d.md`. `task examples:check` validates against live SavedVariables (`ZO_Ingame.lua` / `CharacterMarkdown.lua`); remove example profiles whose triple is missing from SV. Solaegis paired profile + `{slug}_plan.md` live under `examples/solaegis/na/` and `examples/solaegis/eu/` (same slug may exist on both megaservers as separate identities; NA `dolu_tenasi` and EU `dolu_tanesi` are distinct spellings/identities—do not merge them); **paired plans must be build guides** from `template_plan.md`, not profile exports saved as `_plan.md`. When renaming a character identity, rename both `{slug}.md` and `{slug}_plan.md` to the new slug and update internal links. Non-character docs live in `examples/fixtures/`. Paired profiles should link to their plan with a section anchor table and highlight the checklist as the primary in-game entry point.
- Solaegis-style build plans follow the canonical layout in `docs/plan_structure.md`; use `examples/templates/template_plan.md` as the copy-paste skeleton (`build_plan_template.md` is a legacy alias). Filled exemplars: `silent_snow_falls_plan.md`, `kellen_dysart_plan.md`. Reference `docs/subclassing.md` for Trinity / subclassing theory. **Update 49 Dragonknight refresh** (March 2026): use current names and line ownership in `docs/dragonknight_u49.md` — never recommend pre-U49 paths (**Fiery Breath → Noxious Breath**, **Spiked Armor → Hardened Armor**, **Venomous Claw**, **Green Dragon Blood**, etc.); **Earthspike Mantle / Earthshield Mantle** are **Earthen Heart** (not Draconic); **Dragonfire Breath / Disintegrating Dragonfire** are **Draconic Power**; DK class damage is flame (not poison); **Combustion** refunds only on **Burning** with Ardent slotted; **Standard of Might** is a support banner (WD/SD + DR), not a planted DoT — use **Shifting Standard** for the old Defile banner. CP recommendations use exact star names and caps from `examples/templates/champion_points_reference.md` (generated from `champion_points.yaml`); when allocating points, walk `champion_points.yaml` `prerequisites` (`[{star, min_points}, …]`) and fill ancestor minimums before children — the reference.md listing alone does not encode the tree.
- **Build plan H2 order (required for new and heavily revised plans):** (1) title + profile link + pitch, (2) **Build at a glance** (stats, mundus, sets, bars, companion, primary mount, flavor pet, costume + doc-map links), (3) **Roleplay**, (4) **Trinity configuration** (mermaid + one unified table), (5) **Combat kit** (`### Skill bars`, `### Rotation`, `### Passive skills`), (6) **Gear and crafting** (`### Set rationale`, `### Target loadout`, `### Crafting handoff`), (7) **Champion Point Mapping**, (8) **Companion strategy**, (9) **Collectibles** (`### Mount`, `### Pet`, `### Costume`, `### Dye and style`), (10) **Next steps / in-game checklist** with gear phases as labeled steps — no separate Gear Phases H2.
- **Build plan structural rules:** one execution checklist only (merge gear phases into it); no duplicate H2 emoji/titles; trinity = mermaid + one table (no third slot-only table); after any Trinity change, re-validate every slotted skill against the locked lines and keep pitch / Build at a glance / Build Notes / bars in sync with that Trinity; mount and visual identity under Collectibles, never between Gear and Champion Points; **Roleplay** includes **Suggested Custom Title** (≤100 chars) and **Build Notes** paste text (≤1,900 chars, roleplay-first, markdown OK) for LAM; **Companion strategy** uses **Loadout** + **Acquisition** rows per companion tier (never **Core Sets** with player set names); optional Tier B polish when creating plans — use Gear and Crafting subsections and passives immediately after skill bars within Combat kit; **dual Armory** plans keep both loadouts when reordering which is first for in-game setup, and share skill points efficiently across the two kits.
- Crafting support specs for builds may be separate markdown files (e.g. `examples/fixtures/karakedi_crafting.md`) referenced from the main plan; `examples/solaegis/na/masisi.md` and `examples/solaegis/eu/masisi.md` document the account crafter on each megaserver for gear-crafting plans tied to other Solaegis characters on that server.
- ESOUI listing uploads (`README_ESOUI.txt` description, `CHANGELOG.md`) must be **ASCII-only** — UTF-8 punctuation/emojis mojibake on the listing page. Release upload API field is **`compatible`** (not `compatibility`) for the game version badge (e.g. `12.0.0`); set via `.github/workflows/release.yaml` `ESO_API_VERSION` or `scripts/esoui-upload.sh`. **PC-only on ESOUI**: ship release manifest as **`CharacterMarkdown.txt`** (not `.addon`); ZIP root folder must match manifest basename; exclude dev/hidden paths (`__MACOSX`, `.github`, `scripts/`, dotfiles, `.sh`). Account-wide SavedVariables should be **server-scoped** via `ZO_SavedVars` namespace (`GetWorldName()`), not shared across NA/EU/PTS. Listing description needs top-of-page **AI disclosure** and **credits** ([ESOUI rules t=10790](https://www.esoui.com/forums/showthread.php?t=10790)). ESOUI compliance: canonical rules in `docs/ESOUI_BEST_PRACTICES.md`; repo status in `docs/ESOUI_COMPLIANCE.md`. Before release run `task validate:esoui`. Manifest lines must be ≤301 bytes; `## AddOnVersion:` must be a positive integer (not semver). Per-character SavedVars store only `customNotes` / `customTitle` / `playStyle` (+ metadata), never cached markdown.
- Prefer **`/cm`** in all user-facing docs, examples, and code comments; keep **`/markdown`** only as a supported alias (never as the primary command). Optional addon libraries (`OptionalDependsOn` in manifest): LibAddonMenu-2.0, LibDebugLogger, LibSets, LibSlashCommander, LibChatMessage, LibAsync, LibCustomIcons — integrations in `src/utils/` with graceful fallbacks when absent. **AI / Build Coach:** `/cm coach` (aliases `ai`, `build-coach`) emits a compact advice-oriented schema independent of current LAM toggles (`src/generators/BuildCoach.lua`) including collectibles (active mount/costume/pet + owned mounts/pets/costumes); LAM also has **Preset: AI / Build Coach** for leaner normal exports (enables Collectibles detailed + Appearance). **Armory Builds** is first-class (no longer BETA): `includeArmoryBuilds` factory Off, On in Solo PvE / PvP; exports alternate loadouts without swapping gear.
- CharacterMarkdown exports in `examples/` are source of truth for in-game state; they are not necessarily **factory defaults**—many match a LAM preset (e.g. `silent_snow_falls.md` = Solo PvE). Use `scripts/validate_example_preset.py` (`--profile factory-defaults` or `solo-pve`, or `auto`) when auditing section inclusion. When saving multi-chunk exports as examples, copy each chunk once in order—overlapping paste can duplicate sections or corrupt fenced-code boundaries (notably Champion Points diagram/legend `mermaid` blocks; regenerate or repair manually—generator now uses a single mermaid block plus chunking fence guards). When syncing a plan from a profile, label **live** (equipped) vs **target** in Build at a glance and gear, keep skill bars aligned with slotted actives and equipped weapons from the export, and prefer the live character's bar **slot order** when aligning plan bars. Always include a **costume** recommendation in build plans (Collectibles / Build at a glance per `template_plan.md`), choosing only from costumes the account already owns/unlocked in the paired profile export—not unowned store or theoretical options.
- `docs/settings-presets-matrix.md` is the canonical matrix of factory defaults vs LAM presets (Minimal, AI / Build Coach, Solo PvE, PvP Build, Achievement Hunter, Crafter) for every settings-menu checkbox; keep it in sync whenever settings code changes. LAM presets call `ToggleAllSections(false)` first; any checkbox not turned back on by the preset stays off until Reset to Defaults or manual toggle. Solo PvE enables `includeWorldProgress` and `includeAppearance` (post-P50); other opt-in toggles include `includeAchievementDetail`, `includeItemSetCollection`, `includeVengeance`, `includeEndlessDungeon`, and `includeArmoryBuilds`.
- Before removing or rewriting ESO API call sites, verify disputed function/event names against the bundled `ESOUIDocumentationP50.txt` (and in-game globals when needed). **Action bar slot constants** (`ACTION_BAR_ULTIMATE_SLOT_INDEX`, etc.) are **0-based**; `GetSlotBoundId` and related bar APIs use **1-based** indices (ultimate = slot 8). For mounts, `GetMountSkinId()` returns the **cosmetic skin** ID; use `GetActiveCollectibleByType(COLLECTIBLE_CATEGORY_TYPE_MOUNT, actorCategory)` for the equipped mount collectible. Prefer `GetUnitActiveMundusStoneBuffIndices` over buff-name heuristics for active mundus stones. Vanilla Gameplay / Interface / Nameplates / Camera / Combat options are **server-side per character** (not copyable from `UserSettings.txt`); that local file is mostly graphics / audio / mouse and is already shared across characters on this machine.
- Markdown table of contents lists only sections whose generators produced non-empty body content (two-pass generation), not registry conditions alone. Section inclusion and TOC must honor settings booleans (e.g. `includeCollectibles`); mismatches between enabled settings and missing/empty sections are bugs.
